# 04 — Live schema audit (PantherWatch Supabase)

Date: 2026-10-25 local (queries ran at about 2026-10-26 03:04 UTC). The audit was read-only and went through the Supabase MCP connector. Only `SELECT`/`SHOW`, `list_*` and `get_advisors` were used. No DDL or DML was run, and the only file written was this one. Personal data is reported as counts only.

**Target.** `list_projects` returns exactly one project, **PantherWatch**, ref **`movyaglwmwaunkowajxu`**. It is in us-east-1, status ACTIVE_HEALTHY, Postgres engine 17 (supabase-postgres 17.4.1.074), and was created 2025-08-28. This is the expected ref, so no substitution was needed. `list_migrations` is empty: the schema was created by Hibernate `ddl-auto=update`, not by Supabase migrations.

## Headline findings

1. **The app's working tables are empty right now.** `watched_classes`, `user_schedules` and `email_logs` have 0 rows. `users` has 27 rows and `announcements` has 1. The cause is the app's own purge jobs, not data loss:
   - `WatchedClassCleanup` (08:00 daily) deletes all rows for expired and view-only terms.
   - `EmailService.cleanupOldEmailLogs` (02:00 daily) deletes logs older than 1 week.

   Sequence high-water marks show past use: watched_classes 89 ids, email_logs 123, user_schedules 12, announcements 2.
2. **RLS is disabled on all 5 public tables, and `anon` and `authenticated` have full grants on them.** The grants are SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES and TRIGGER. Anyone with the project's anon key can read or wipe the users table (27 rows) through PostgREST. This is the advisor's only ERROR.
3. **The `email_logs.email_type` CHECK is frozen at three values** (`WELCOME`, `GOODBYE`, `CLASS_AVAILABILITY`). `ddl-auto=update` never rewrites an existing CHECK. Any new `EmailType` constant will fail on insert until the constraint is changed by hand.
4. **`public.users` and `auth.users` have drifted apart.** There are 27 public users and 23 auth users, and only 21 are linked by id. 6 public users have no auth row, and 2 auth users have no public row. Auth signups stop at 2026-05-25, but public users continue to 2026-07-31. That fits the move to direct Google sign-in keyed by `google_sub`, where Supabase Auth is no longer the source of truth. 19 of 27 users still have a null `google_sub`.
5. **None of the legacy columns or tables exist.** These are `last_checked_at`, `last_known_*`, `last_notified_at`, `google_id`, `phone_number` and `notification_logs`. The one leftover column is `email_logs.crn`, which no entity maps.

**Performance**: no lints. The tables are too small to trigger unused-index or seq-scan advisories. The only FK (`watched_classes.user_id`) is covered by the leading column of the unique index.

**What this means for the new schema.** The backend connects as a privileged role over JDBC, and the frontend never uses PostgREST. Either enable RLS with no policies, which denies `anon` and `authenticated` while the backend's role bypasses or owns the tables, or `REVOKE ALL ... FROM anon, authenticated`. Stopping exposure of `public` in the Data API settings also works. The remediation SQL the tool suggested was **not** run:

```sql
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;  -- and the same for the other 4 tables
```

Before relying on the RLS option, confirm which role the backend's JDBC user is. If it is `postgres`, it owns the tables and bypasses RLS.

## Differences from what the code expects

The code compared is the entities in `backend/src/main/java/edu/gsu/pantherwatch/pantherwatch/model/`: `Announcement`, `EmailLog`, `User`, `UserSchedule` and `WatchedClass`. `SectionGrade` is in-memory only, and correctly has no table. `application.properties` sets `spring.jpa.hibernate.ddl-auto=update`. Hibernate can therefore add tables and columns, but it never drops, retypes or re-constrains them.

### Extra in the DB (legacy)

| Object | Notes |
|---|---|
| `email_logs.crn varchar(10) NULL` | Not mapped by `EmailLog`, and no Java code reads or writes it. It is always null for rows Hibernate inserts. It is a leftover from an earlier per-CRN dedup design. Either drop it, or map it if per-CRN dedup comes back. The current dedup uses `subject LIKE`. |
| `watched_classes UNIQUE (user_id, crn, term)` (`uksss08yywl2um9n2uqdnexu0l5`) | It exists in the DB, but `WatchedClass` declares no `@UniqueConstraint`. It is a useful constraint: keep it, and declare it in the entity or the new DDL so a fresh database gets it too. |

There are no extra tables, views, functions or triggers.

### Missing constraints and indexes the code assumes or would benefit from

| Gap | Why it matters |
|---|---|
| No FK `user_schedules.user_id → users.user_id` | `UserSchedule.userId` is a bare `UUID`, not a `@ManyToOne`, so Hibernate never created an FK. Deleting a user with JPQL or SQL leaves orphaned schedules. There are 0 orphans today only because the table is empty. |
| `watched_classes` FK has no `ON DELETE CASCADE` | Any deletion of a user has to remove watched classes first in code, or it fails with an FK violation. |
| No FK or link from `users.user_id` to `auth.users.id` | This is intentional now that `google_sub` is the identity, but it explains the 6 + 2 mismatched rows. The new schema should drop the assumption that `user_id` equals the Supabase auth uid. |
| No UNIQUE on `users.google_sub` | The code looks users up by `google_sub`. There are no duplicates today (0), but nothing prevents them. Use a partial unique index `WHERE google_sub IS NOT NULL` while 19 rows are null. |
| `users.email` UNIQUE is case-sensitive | 0 mixed-case rows exist today. If lookups lower-case the email, use `UNIQUE (lower(email))` or `citext`. `citext` is available but not installed. |
| No index on `watched_classes(term)` or `user_schedules(term_code)` | These columns drive `findDistinctTerms`, `deleteByTermIn`, `findDistinctTermCodes` and `deleteByTermCodeIn`. The tables are tiny, so this is optional. |
| No index on `email_logs(email, email_type, sent_at)` | It would serve the spam-check queries in `EmailLogRepository`. The table holds at most about a week of rows, so this is optional. |
| No CHECK on `announcements.type` | The entity defaults to `"warning"`. Any string is accepted. |

### The exact Hibernate CHECK on `email_logs.email_type`

```
email_logs_email_type_check:
CHECK (((email_type)::text = ANY ((ARRAY['WELCOME'::character varying, 'GOODBYE'::character varying, 'CLASS_AVAILABILITY'::character varying])::text[])))
```

This matches the current `EmailLog.EmailType` enum exactly: `WELCOME`, `GOODBYE`, `CLASS_AVAILABILITY`. Hibernate 6 generated it from `@Enumerated(EnumType.STRING)` when the table was created. **`ddl-auto=update` will not change it.** If a constant is added to `EmailType`, every insert with the new value fails with `23514 check_violation` until the constraint is dropped and recreated by hand. The new schema should either own this CHECK in explicit DDL and change it together with the enum, or replace it with a lookup table.
